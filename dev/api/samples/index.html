Sample-based analysis

Outcome tables from model runs, utilities counted in individuals, the estimators of the value of information with their standard errors, and decision sensitivity.

Outcome tables

DecisionAnalysis.OutcomeTable — Type
OutcomeTable(runs; draw=:draw, action=:action, replicate=:replicate, outcomes,
             status=nothing, ok=("ok",), parameters=nothing, key=draw,
             weights=nothing, actions=nothing)

The outcomes of a model over draws × actions × replicates × named outcomes, built from runs, any Tables.jl table with one row per run (a vector of named tuples, a data frame, a CSV file read into a table). The keywords name its columns:

  • draw, action, replicate: the columns that identify the parameter draw, the action and the replicate of each run. Their values become labels (Symbol of their text), in order of first appearance. A run that appears twice throws InvalidOutcomeError.
  • outcomes: the names of the outcome columns to keep (numbers).
  • status: the name of a column that says whether a run succeeded, and ok the values that count as success. A run with any other status is kept and counted, never silently dropped: it is left out of every mean and standard error, and it is listed by failed_runs and counted by run_counts. Without status every run counts as a success, and its outcomes must be finite.
  • parameters: the parameter values of the draws. Either a Tables.jl table with one row per draw and a column named by key (default: the name given as draw) that identifies it, or a list of column names of runs itself (each constant within a draw). With a table, the draws take its row order, and every draw of runs must be in it.
  • weights: the weights of the draws: nothing (equal), a vector in draw order, or the name of a column of the parameters table. They are normalised as for a SampleBelief.
  • actions: the order of the actions, when the order of first appearance is not the one wanted (a permutation of the labels found).

Cells need not have the same number of runs: replicates that are absent or failed are simply not averaged. A cell with no usable run is allowed in the table, and payoff_table refuses to make a payoff from it.

The table is the seam with model packages: a model package writes a table of runs (or implements the adapter verbs for outcomes) and knows nothing of this package. A utility turns it into a payoff table: payoff_table.

Accessors: state_labels (the draws), action_labels, outcome_names, parameter_draws, draw_weights, replicate_counts, run_counts, failed_runs, and SampleBelief(table).

julia> runs = [(; draw=d, action=a, replicate=r, frogs=10d + (a == "fence") + r)
               for d in 1:2 for a in ("none", "fence") for r in 1:3];

julia> t = OutcomeTable(runs; outcomes=[:frogs]);

julia> run_counts(t)
(runs = 12, ok = 12, failed = 0, absent = 0)

julia> payoff_table(t, IndividualsUtility(:frogs)).Q
2×2 Matrix{Rational{Int64}}:
 12  22
 13  23

DecisionAnalysis.outcomes — Function
outcomes(prob, actions, draws; replicates=1, seed) -> OutcomeTable

Run a model over draws × actions × replicates and collect the named outcomes. The model is reached through the adapter verbs only, which must have methods for the type of prob: each run is

outcome(simulate(apply_action(with_parameters(prob, θ), a); rng))

(with_parameters, apply_action, simulate, outcome).

  • actions: the actions, as label => action pairs, a named tuple, a dictionary, or a list of values that are their own labels. Include no intervention.
  • draws: a SampleBelief, or a Tables.jl table of parameter draws (equal weights). Each θ is one row, a named tuple. Draws are propagated one by one; a mean of the parameters is never plugged in.
  • replicates: runs per cell. A stochastic model needs several, so that a cell of the payoff table is a conditional expectation and has a standard error; a table with one is flagged (single_replicate).
  • seed: an integer, required. Common random numbers: the run of replicate r at draw d gets a Random.Xoshiro whose seed is a fixed integer hash of (seed, d, r), the same for every action, so the difference between two actions in a cell is not blurred by different random numbers. How long two runs stay comparable after an intervention is up to the model (see simulate).

A run that throws is kept as a failed run with the status error:<exception type> (see failed_runs); an InterruptException is rethrown. If every run fails, InvalidOutcomeError is thrown with the first error's message.

DecisionAnalysis.crn_correlation — Function
crn_correlation(outcomes::OutcomeTable, utility) -> Float64

The achieved correlation between actions of the simulation noise within a cell: the pooled correlation, over draws and pairs of actions, of the utilities of the same replicate under two actions (deviations from each cell's mean). Under common random numbers (outcomes) it is positive, and the closer to one, the more of the noise cancels in a comparison of actions; independent runs give about zero. Pass it as noise_correlation to evpi with SampleAverage and to DecisionReport, so that the cell-noise bias is not overstated. NaN when there is no noise to correlate.

Adapter verbs

DecisionAnalysis.with_parameters — Function
with_parameters(prob, θ)

Adapter verb, to be given methods for a model's problem type: the problem prob with its uncertain parameters set to the draw θ, a named tuple holding one row of the parameter draws. It must not mutate prob. The package defines no method.

The four verbs are used by outcomes in this order: outcome(simulate(apply_action(with_parameters(prob, θ), a); rng)).

source
DecisionAnalysis.apply_action — Function
apply_action(prob, action)

Adapter verb, to be given methods for a model's problem type: the problem prob under the intervention action. An action is an intervention on the model (a changed rate, a pulse on a given day, a control switched on), and the method documents how each action changes it; no intervention must be an action too, so that every analysis has its baseline. It must not mutate prob. The package defines no method.

source
DecisionAnalysis.simulate — Function
simulate(prob; rng)

Adapter verb, to be given methods for a model's problem type: one run of the model, drawing every random number from rng. outcomes passes a Random.Xoshiro seeded identically for every action at a given draw and replicate (common random numbers), so a deterministic model can ignore rng and a stochastic one must use nothing else. An individual-based model keeps runs comparable for longer after an intervention if it derives one stream per individual from rng instead of drawing from a single stream in event order. The package defines no method.

Outcomes are counts or other quantities of the model, not utilities: the utility is applied afterwards by payoff_table. The package defines no method.

Utilities

DecisionAnalysis.AbstractUtility — Type
AbstractUtility

Supertype of the utilities that payoff_table applies to an OutcomeTable. The count utilities IndividualsUtility and InfectionUtility are linear, so their expected utility is an expected number of individuals. The risk-attitude utilities LinearUtility, ExponentialUtility and PowerUtility act on one named outcome, and AdditiveUtility and MultiplicativeUtility combine several attributes; FunctionUtility wraps any function. A utility is callable on the named outcomes of one run: u((; uninfected=40, infected=3)). Outcomes are counts of individuals of the focal species; there are no monetary costs.

source
DecisionAnalysis.IndividualsUtility — Type
IndividualsUtility(name)

The utility that counts individuals: the value of the outcome called name (the number of the focal species at the evaluation time). It is linear, so expected utility is an expected number of individuals and every value of information is read in individuals. The count must not be negative.

julia> IndividualsUtility(:frogs)((; frogs=12, eggs=300))
12
source
DecisionAnalysis.InfectionUtility — Type
InfectionUtility(; uninfected=:uninfected, infected=:infected, weight=1)

The utility for an infectious disease, from two counts of one run:

utility = uninfected − weight × infected.

uninfected and infected name the outcomes that hold the two counts. Uninfected individuals count for one each and every infected individual counts against, with weight ≥ 0 the one free parameter: weight = 0 counts only the uninfected and weight = 1 sets an infected individual against an uninfected one. The weight is a value judgement, so show results at 0, at 1 and as a sweep (policy_regions). Whether infected but living individuals also count towards the population is a modelling choice: to count every survivor, use IndividualsUtility on the number alive.

This is the utility behind infection_payoff, which applies it to tables of counts.

julia> InfectionUtility(; weight=1 // 2)((; uninfected=40, infected=6))
37//1

DecisionAnalysis.FunctionUtility — Type
FunctionUtility(f; name=:utility)

A utility given by a function of the named outcomes of one run: f(o::NamedTuple) -> Real, for example FunctionUtility(o -> o.survivors / o.initial) for the surviving fraction. Passing a plain function to payoff_table wraps it in this type. Keep the result in units of individuals (or a fraction of them); the package has no monetary costs.

DecisionAnalysis.payoff_table — Function
payoff_table(outcomes::OutcomeTable, utility; baseline=nothing) -> PayoffTable

The payoff table of an outcome table under a utility: Q[a, θ] is the conditional expected utility of action a at draw θ, the mean of the utility over the usable replicates of the cell. utility is an AbstractUtility (IndividualsUtility, InfectionUtility, the risk-attitude utilities LinearUtility, ExponentialUtility and PowerUtility, the multi-attribute AdditiveUtility and MultiplicativeUtility, FunctionUtility) or a plain function of the named outcomes of one run.

The utility is applied to each run, before anything is averaged over replicates. A non-linear utility of the mean outcome is not the mean utility (Jensen's inequality), so averaging the outcomes first would be wrong for every utility but a linear one. With a non-linear utility the payoffs, and every expected utility and value of information computed from them, are in units of utility and no longer counts of individuals; certainty_equivalent takes an expected utility back to individuals.

Monte Carlo error is kept apart. The result carries standard_errors, the standard error of each cell mean (sample standard deviation over √n), and replicates, the number of runs averaged; neither is folded into a payoff. A cell with one run has no standard error: the table then has standard_errors = nothing and is flagged by single_replicate. Runs with a failing status are left out, and a cell with no usable run throws InvalidOutcomeError.

Gains over no intervention. With baseline (an action label), the table holds the gain of each action over the baseline, Q[a, θ] − Q[baseline, θ], computed replicate by replicate from the runs that both have (the same replicate uses the same random numbers under outcomes), so its standard errors are those of the paired differences and are smaller than independent runs would give. The baseline row is zero. Regret and every value of information are the same for the gains as for the payoffs.

Exact in, exact out: integer or rational utilities give rational payoffs; standard errors are floating point.

julia> runs = [(; draw=d, action=a, replicate=r, uninfected=20d + r, infected=(a == "none") * 4r)
               for d in 1:2 for a in ("none", "treat") for r in 1:2];

julia> t = OutcomeTable(runs; outcomes=[:uninfected, :infected]);

julia> payoff_table(t, InfectionUtility(; weight=1); baseline=:none).Q
2×2 Matrix{Rational{Int64}}:
 0  0
 6  6

Estimates and their errors

DecisionAnalysis.VOIEstimate — Type
VOIEstimate

A sample-based estimate of a value of information, as returned by evpi, evppi and evsi when they are called with a method. Fields:

  • quantity: :evpi, :evppi or :evsi; method: the name of the method.
  • value: the estimate, in the units of the payoff (individuals).
  • standard_error: the Monte Carlo standard error of value from the finite number of draws (and, for importance sampling, of simulated data sets as well: see ImportanceSampling), kept apart and never folded into the value. By default it is the linearised error of the weighted mean of the per-draw policy gains Q[â_i, i] − Q[a*, i]: what following the fitted policy (the action â_i with the largest fitted conditional mean at draw i) gains over the act-now action a*, evaluated on the payoffs themselves. To first order this is the error of the estimate including the uncertainty of the fit (for cell means it is exact, and the mean of the policy gains is the estimate). With bootstrap = B it is instead the standard deviation over B resamples of the draws with the fit redone each time.
  • bias: a named tuple of the two selection biases that the optimiser's curse puts into the two terms of the estimate, each an estimate of an upward bias in one term (the expected maximum of unbiased estimates is at least the maximum of what they estimate), and again not subtracted: act_now is the upward bias of the act-now value max_a Σ_i w_i Q[a, i] from maximising sample means: the best reported value overstates, on average, what the chosen action is worth; cells is the upward bias of the perfect-information value Σ_i w_i max_a Q[a, i] from maximising noisy cell means (zero for a table with no standard errors, and nothing for methods that smooth over the noise). A value of information is the difference of two such terms, so the sign of its bias is not determined in general: act_now pulls it down and cells pulls a plain SampleAverage EVPI up. With exact cells only the first acts, and the plain EVPI of a sample is biased downwards. Both are plug-in normal approximations, simulated with a seeded Xoshiro; cells takes the noise of the actions in a cell to be independent unless a noise_correlation is given, and so overstates the bias under common random numbers (see crn_correlation).
  • details: method-specific diagnostics (act-now value and action, effective sample sizes, residual variance, ...). For importance sampling the posterior effective sample sizes are part of the estimate and are printed with it.

Float64(e) and e.value give the number; arithmetic is deliberately not defined, so that an error cannot be dropped by accident.

source
DecisionAnalysis.expected_utility_estimates — Function
expected_utility_estimates(problem::DecisionProblem) -> Vector{NamedTuple}

The expected utility of every feasible action of a sample problem, with its Monte Carlo error, one (; action, value, standard_error, simulation_error) per action:

  • value: Σ_i w_i Q[a, i], as aggregate(Expectation(), problem);
  • standard_error: the error of that mean when the draws are a random sample of the belief, from the spread of the cell means across draws (which already contains the simulation noise of the cells);
  • simulation_error: the error from the simulator alone, holding the draws fixed, from the standard errors of the cells (nothing when the table has none). This is the relevant error when the draws are a fixed design.

For the expected gain over the baseline with the right (paired) errors, build the problem on a table of gains: payoff_table(outcomes, utility; baseline).

source
DecisionAnalysis.expected_gain_estimates — Function
expected_gain_estimates(problem::DecisionProblem) -> Vector{NamedTuple}

The expected gain of every feasible action over the baseline of a sample problem, one (; action, value, standard_error) per action. value is expected_gain_over_baseline; standard_error is the error of the weighted mean of the per-draw gains Q[a, i] − Q[baseline, i] when the draws are a random sample, so the correlation between an action and the baseline across draws is accounted for. Throws MissingBaselineError without a baseline.

source
DecisionAnalysis.variance_components — Function
variance_components(problem::DecisionProblem) -> Vector{NamedTuple}

The analysis-of-variance split of each feasible action's payoff between parameter and simulation variance, for a sample problem whose table has standard errors. One (; action, total, simulation, parameter, parameter_share) per action:

  • total: the weighted variance of the cell means across the draws;
  • simulation: the weighted mean of the squared standard errors of the cells, the part of total that is simulation noise left in the cell means;
  • parameter = total − simulation: the variance of the conditional expected payoff across draws, which is what information about the parameters can act on. It is returned as computed, so it can be slightly negative when noise dominates;
  • parameter_share = parameter / total.

A small parameter share says that the cells need more replicates before a SampleAverage value of information means much. To split the variance of a difference between two actions, apply this to a table of gains (payoff_table(outcomes, utility; baseline)).

source
DecisionAnalysis.conditional_problem — Function
conditional_problem(problem::DecisionProblem, focal) -> DecisionProblem

The sample problem collapsed onto a discrete parameter: a finite problem whose states are the cells of focal (a parameter name, or several, of the draws of a SampleBelief; one cell per combination of values, in sorted order when the values can be sorted and otherwise in order of first appearance), whose payoffs are the weighted mean payoffs of the feasible actions within each cell, and whose belief is the FiniteBelief of the cells' total weights. Feasibility and baseline carry over.

It is the table a manager would look at when the cell is what could be learned: the expected payoff of each action by group. Its evpi is the grouping estimate of the EVPPI of focal (evppi(problem, focal, Grouping())), and with a ScenarioSet over its states the cells become scenarios for maximin and minimax regret, without weights. Each cell mean is an estimate from the draws in the cell; cells with few draws are noisy.

julia> belief = SampleBelief((; site=[:wet, :wet, :dry, :dry]));

julia> p = DecisionProblem(PayoffTable([0 0 0 0; 2 4 -4 -6]), belief);

julia> c = conditional_problem(p, :site); (state_labels(c), c.payoff.Q)
([:dry, :wet], Rational{Int64}[0 0; -5 3])

julia> evpi(c) == evppi(p, :site).value
true

Methods

DecisionAnalysis.AbstractVOIMethod — Type
AbstractVOIMethod

Supertype of the methods that estimate a value of information from a SampleBelief: SampleAverage, Grouping, StrongOakley, Sadatsafavi and the regressions (AbstractRegression: SplineRegression, GAMRegression, GaussianProcessRegression).

source
DecisionAnalysis.AbstractRegression — Type
AbstractRegression <: AbstractVOIMethod

Supertype of the regression methods, which estimate the conditional mean of every action's payoff given some columns (parameters or summary statistics) by regressing the payoffs on them: SplineRegression (built in), GAMRegression (extension, needs GAM.jl) and GaussianProcessRegression (built in, for five or more columns). A regression smooths over the simulation noise of the cells, so it is the estimator to use when cells are noisy.

source
DecisionAnalysis.SampleAverage — Type
SampleAverage()

The plain estimator: the definition applied to the sample as it stands. For evpi it is Σ_i w_i max_a Q[a, i] − max_a Σ_i w_i Q[a, i], the number that evpi(problem) returns, now with its standard error and its two biases. It is right for a table of exact conditional expectations; for a table of noisy cell means its perfect-information term maximises over the noise and is biased upwards (see VOIEstimate), and a regression is the better estimator.

source
DecisionAnalysis.Grouping — Type
Grouping(; bins=nothing)

EVPPI for a discrete (grouping) variable: the conditional mean of each action's payoff is its weighted mean within each cell, where a cell is one combination of values of the focal columns. It is the estimator for a categorical parameter such as a scenario label or a group, and it is evppi(problem, partition) with the partition read from the draws. With bins = k, a single numeric focal parameter is first cut into k bins of equal weight. Cells with few draws make the estimate noisy and bias its value-with-information term upwards; the result reports the smallest cell.

source
DecisionAnalysis.StrongOakley — Type
StrongOakley(; blocks=nothing)

Single-parameter EVPPI by the method of Strong and Oakley (2013, Medical Decision Making 33:755): sort the draws by the focal parameter, cut them into blocks consecutive blocks of equal weight, and take each action's mean payoff within a block as its conditional mean there. No regression and no extra dependency. More blocks follow the conditional mean more closely but average fewer draws each, which biases the value-with-information term upwards; blocks = nothing uses clamp(round(√n / 2), 2, 50).

source
DecisionAnalysis.Sadatsafavi — Type
Sadatsafavi(; separators=1)

Single-parameter EVPPI by the method of Sadatsafavi, Bansback, Zafari, Najafzadeh and Marra (2013, Value in Health 16:438): sort the draws by the focal parameter and find the separators cut points (one or two) that maximise the value of choosing the best action separately in each segment. It is exact, as the sample grows, when the best action changes at most separators times along the parameter. The search is exhaustive: every position is tried for one cut, and every pair of positions for two (in time proportional to draws × actions, by a running maximum), so the value with two separators is never below the value with one. Choosing the cuts to maximise the value biases the value-with-information term upwards in small samples.

Checked against the R package voi (1.0.3, method "sal") on the same draws: with one and with two separators the two agree to rounding (relative differences below 1e-9) on the normal model of its vignette and on its chemotherapy example, both of which have two actions. With more than two actions voi places the cuts pair of actions by pair of actions, which need not give the best segmentation, so this estimate can be larger than its value there. The fixtures and the numbers are in test/fixtures/voi and validation/.

source
DecisionAnalysis.SplineRegression — Type
SplineRegression(; knots=4, degree=3, interactions=false)

The built-in regression: an additive regression spline fitted by weighted least squares, with no dependency beyond LinearAlgebra. Each numeric column enters through a truncated-power spline basis of the given degree with knots interior knots at weighted quantiles; a non-numeric column, or a numeric one with no more distinct values than the basis has functions, enters as a factor (one mean per level), so that the fit reproduces cell means exactly when the columns are discrete. With interactions = true the products of the basis functions of every pair of columns are added (a tensor-product surface per pair), which needs many more draws.

It is meant for up to about four columns. There is no penalty and no smoothing parameter: the flexibility is set by knots, and SplineRegression(; knots=0, degree=1) is the linear metamodel of Jalal, Goldhaber-Fiebert and Kuntz (2015). For penalised smooths use GAMRegression, and for five or more columns GaussianProcessRegression.

source
DecisionAnalysis.GAMRegression — Type
GAMRegression(; k=10, tensor=false)

Regression by a generalised additive model with penalised smooths, fitted by GAM.jl (github.com/ecorecipes/GAM.jl): one smooth s(x, k = k) per numeric column, or a tensor-product smooth of all of them with tensor = true; non-numeric columns enter as factors. This is the regression that the R package voi uses by default for up to four parameters (Strong, Oakley and Brennan 2014).

The method lives in a weak-dependency extension: load GAM.jl (using GAM) before using it, otherwise MissingExtensionError is thrown. GAM.jl is not a dependency of this package.

source
DecisionAnalysis.GaussianProcessRegression — Type
GaussianProcessRegression(; max_points=1500, hyper_points=250, seed=1,
                          min_nugget=1e-8, min_length_scale=1)

Regression by a Gaussian process, the method for five or more focal parameters (Strong, Oakley and Brennan 2014, Medical Decision Making 34:311), built in with no dependency beyond LinearAlgebra. Each action's payoff is modelled as

Q[a, i] = β₀ + βᵀ x_i + f(x_i) + ε_i,

a linear mean, a Gaussian process f with the squared-exponential correlation c(x, x′) = exp(−Σ_j ((x_j − x′_j) / δ_j)²), one length scale δ_j per column, and independent noise with variance ν times that of f (the nugget), which stands for everything the columns do not explain: the other parameters and the simulation noise of the cells. The columns are standardised first. β and the variance are integrated out under flat priors, and the hyperparameters δ and ν are set, for each action separately, by maximising the resulting marginal likelihood with a Nelder-Mead search from a fixed start. The fitted conditional means are the posterior mean of β₀ + βᵀ x + f(x) at every draw.

The cost of a Gaussian process grows with the cube of the number of points, so two subsamples of the draws are used, both chosen with a Xoshiro(seed):

  • hyper_points: the number of draws used to estimate the hyperparameters;
  • max_points: the largest number of draws the process is conditioned on. With more draws than this, the process is fitted to a subsample and predicts the conditional means of all the draws, so every draw still enters the estimate.

A draw's weight divides its noise variance; draws of weight zero are not used in the fit. min_nugget is the smallest nugget the search may choose (relative to the variance of f); it also keeps the linear algebra stable.

The length scales are bounded below, at min_length_scale times the median distance between neighbouring points of the subsample used for the hyperparameters (in standardised coordinates). A process with shorter length scales is independent noise at the points it is fitted to: the likelihood cannot tell it from the nugget, but its fitted values would reproduce the payoffs, noise included, and the estimate would drift up to the EVPI. With many parameters the points are far apart, so the bound is what keeps the fit a smooth function of them; lower it only for payoffs known to vary on a finer scale than the draws resolve. The columns must be numeric (use Grouping for a discrete parameter); a constant column is dropped.

A Gaussian process does not reproduce cell means of discrete columns exactly, and it is slower than SplineRegression for a few parameters; it is what evppi uses by default from five numeric focal parameters on, where an additive spline would miss the interactions and a tensor-product one has too many coefficients.

source
DecisionAnalysis.fitted_conditional_means — Function
fitted_conditional_means(method::AbstractRegression, columns, Q, w) -> Matrix

The regression step that every regression method implements: the fitted conditional means G[a, i] of each row of Q (actions × draws) given the columns (a named tuple of vectors, one entry per draw), fitted with the draw weights w. The weighted mean of each fitted row must equal that of the row itself (true of any weighted least-squares fit with an intercept). A new regression backend subtypes AbstractRegression and adds a method.

Studies for EVSI

DecisionAnalysis.SummaryStatistics — Type
SummaryStatistics(summaries; regression=SplineRegression())

A study described by summary statistics of its simulated data, for evsi by the regression method of Strong, Oakley, Brennan and Breeze (2015, Medical Decision Making 35:570). summaries is a Tables.jl table with one row per draw: for each draw, one data set is simulated from the study under that draw's parameters, and reduced to a few numbers (a sample mean, a count of positives). The EVSI is then the value of learning the summaries, estimated by regressing the payoffs on them with regression. The summaries must be (close to) sufficient for what the study tells about the parameters, and few: the built-in regression suits up to about four.

DecisionAnalysis.ImportanceSampling — Type
ImportanceSampling(loglikelihood; weights=nothing)

A study described by the likelihood of its simulated data, for evsi by the importance-sampling method of Menzies (2016, Medical Decision Making 36:308). loglikelihood[k, j] is the log-likelihood of simulated data set k under the parameters of draw j (rows = data sets, columns = draws; any additive constant per row is harmless). Data set k must have been simulated from the prior predictive distribution: draw a parameter set from the sample, then data given it.

weights are the weights of the data sets. With nothing, there must be one data set per draw, data set k simulated from draw k, and they take the weights of the draws; if the data sets were instead simulated from draws picked with probability proportional to their weights, pass weights = :equal. A vector gives them explicitly.

For each data set the draws are reweighted by their likelihood, which gives the posterior expected payoff of every action without refitting anything. See importance_loglikelihoods to build the matrix from a data simulator and a log-likelihood function.

Effective sample size. The estimate degrades when the data are so informative that a few draws carry all the weight: each posterior mean is then an average over few draws, the maximum over actions is taken over noisy means, and the estimate drifts upwards towards the EVPI. The result therefore reports the posterior effective sample size 1 / Σ_j π_kj² of the data sets in details (minimum_ess, median_ess, mean_ess, beside prior_ess, that of the draws themselves) and prints the median and the smallest with the estimate. A median of a few tens or less says that more draws are needed, or a regression on summary statistics (SummaryStatistics).

Standard error. The estimate has two sources of Monte Carlo error and standard_error combines them, √(datasets² + draws²), so that it is comparable with the other estimators:

  • details.datasets_standard_error: from the finite number of simulated data sets, the error of the weighted mean of the per-data-set gains;
  • details.draws_standard_error: from the finite number of draws, by the delta method. Each posterior mean is a self-normalised weighted mean over the draws; its linearisation gives the first-order effect of draw j on the whole estimate, Σ_k v_k π_kj (D_kj − g_k), with π_kj the posterior weight of draw j for data set k, D_kj the payoff of the action chosen for data set k minus that of the act-now action at draw j, and g_k its posterior mean; the sum of the squares of these effects over the draws is the variance.

The two are treated as independent, which ignores that a data set was simulated from one of the draws, and the delta method is first-order: with a small effective sample size it understates the error and says nothing of the upward drift above. On the normal model of the R voi vignette (EVSI of 10 or 100 observations of p1; 400 to 2000 draws, 100 to 1000 data sets, 150 repetitions of each of five designs) the reported standard error was between 0.91 and 1.13 times the standard deviation of the estimate over the repetitions; the error from the data sets alone was between 0.27 and 0.79 times.

DecisionAnalysis.importance_loglikelihoods — Function
importance_loglikelihoods(simulate_data, loglikelihood, belief::SampleBelief;
                          datasets=nothing, seed) -> ImportanceSampling

Build the log-likelihood matrix of an ImportanceSampling study from two functions of the user's model:

  • simulate_data(rng, θ): one data set of the study under the parameters θ (a named tuple, one row of the draws);
  • loglikelihood(data, θ): the log-likelihood of that data set under θ.

With datasets = nothing, one data set is simulated from every draw (and they carry the draws' weights). With datasets = K, K draws are picked with probability proportional to their weights and one data set is simulated from each (equal weights). Every random number comes from Xoshiro(seed); seed is required. The cost is K × n likelihood evaluations.

DecisionAnalysis.GaussianApproximation — Type
GaussianApproximation(focal; n0, n, regression=nothing)

A study that measures the focal parameters with n observations, for evsi by the Gaussian approximation of Jalal and Alarid-Escudero (2018, Medical Decision Making 38:174). n0 is the prior effective sample size: the number of observations of the study that the prior on the focal parameters is worth (for a normal prior with variance τ² and observations with variance σ², n0 = σ²/τ²). The conditional means of the payoffs given the focal parameters are fitted once (as for evppi, with regression, or the default method for the columns) and shrunk towards their mean by the factor √(n / (n0 + n)), which approximates their preposterior distribution. One fit therefore gives the EVSI at any sample size: n may be a number or a vector, and with a vector evsi returns one estimate per size, a curve that rises to the EVPPI of the focal parameters.

The approximation is exact when the conditional means are linear in a normal parameter with normal data, and otherwise as good as the normal approximation to the prior and the posterior.

Standard error. The default standard error is the linearised one of VOIEstimate with the residuals of the fit scaled by the shrinkage factor. It covers the sampling of the draws and, to first order, the fit; it does not cover the error of the approximation itself (a wrong n0, a prior or posterior far from normal), which is a bias and not a Monte Carlo error. On the normal model of the R voi vignette (EVSI of 1, 10 and 100 observations of p1; 1000 and 4000 draws, 300 repetitions of each) it was between 1.02 and 1.05 times the standard deviation of the estimate over the repetitions with the default regression, and 1.25 times (conservative) with a linear fit, whose error is smaller than the linearisation allows for; bootstrap = 100 gave 0.94 to 0.99 times.

DecisionAnalysis.policy_regions — Function
policy_regions(base, direction; from=0, to=1) -> Vector{NamedTuple}

The policy regions of a one-parameter family of problems: the intervals of the parameter t on which each action maximises expected utility, when the payoff is

Q(t) = Q_base + t · Q_direction,    from ≤ t ≤ to.

base is a DecisionProblem with a single prior (a finite or sample belief) and direction a PayoffTable with the same labels. Expected utility is linear in t for every action, so the regions are found exactly, as the upper envelope of straight lines: the result is exact for exact inputs, and nothing is gridded. One (; from, to, actions) per region, in order, where actions are the feasible actions that are optimal throughout the region (several when they tie everywhere on it).

This is the weight sweep of the infection utility: with base the problem on the uninfected counts and direction minus the infected counts, t is the weight w in uninfected − w × infected. The interior boundaries are the one_way_thresholds.

julia> uninfected = PayoffTable([:none, :treat], [:low, :high], [90 40; 80 70]);

julia> infected = PayoffTable([:none, :treat], [:low, :high], [10 50; 15 20]);

julia> p = DecisionProblem(uninfected, [1 // 2, 1 // 2]; baseline=:none);

julia> policy_regions(p, -infected; from=0, to=2)
1-element Vector{@NamedTuple{from::Rational{Int64}, to::Rational{Int64}, actions::Vector{Symbol}}}:
 (from = 0, to = 2, actions = [:treat])

DecisionAnalysis.one_way_thresholds — Function
one_way_thresholds(base, direction; from=0, to=1) -> Vector{NamedTuple}

The values of the parameter t at which the action that maximises expected utility changes, for the one-parameter family of policy_regions: one (; threshold, below, above) per switch, with the optimal actions on either side. An empty result says that one choice holds over the whole range, so the decision is insensitive to the parameter there.

DecisionAnalysis.weight_sweep — Function
weight_sweep(build, weights; rule=MaxExpectedUtility()) -> Vector{NamedTuple}

Apply rule to the problem build(w) for every w in weights and tabulate the result: one (; weight, first_choice, chosen, scores, ranking) per weight, where ranking lists the feasible actions from best to worst under the rule's score (ties in table order). build is any function from a weight to a DecisionProblem, so the sweep works for any utility and any rule, for example

weight_sweep(w -> DecisionProblem(outcomes, InfectionUtility(; weight=w);
                                  baseline=:none), 0:0.25:2)

The result is a Tables.jl row table. For expected utility that is linear in the weight, policy_regions gives the switch points exactly instead of on a grid. See rank_reversals for where the order of the actions changes.

DecisionAnalysis.rank_reversals — Function
rank_reversals(sweep) -> Vector{NamedTuple}
rank_reversals(a::DecisionProblem, b::DecisionProblem; aggregator=Expectation())

Rank reversals: pairs of actions whose order differs between two analyses.

The first form takes the result of weight_sweep and compares each weight with the next: one (; from, to, actions, top_changed) per pair of actions that swap between the two weights, where top_changed says whether the first choice itself changed.

The second form compares two problems with the same feasible actions (two utilities, two beliefs, a count and a fraction): one (; actions, top_changed) per pair of actions that the aggregator ranks strictly one way in a and strictly the other way in b. An empty result says that the two analyses order the actions alike, ties aside.
